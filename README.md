# Instamart Copilot

## Overview

Instamart Copilot is an end-to-end customer-intelligence project built on synthetic quick-commerce data (1,200 customers, 40 products, 13,084 raw order rows, 164 support tickets). It has four parts:

- **Part A – Data cleaning, SQL and EDA:** audit and clean the raw CSVs, load them into SQLite, answer seven SQL questions (including window functions) and describe the order-amount distribution.
- **Part B – Segmentation and lapse prediction:** RFM features, K-Means segments, a leakage-free lapse classifier (Logistic Regression vs Random Forest) and a retention list of high-risk Premium customers.
- **Part C – Support-ticket triage with guardrails:** input checks, PII redaction, zero-shot vs few-shot classification through the offline `mock_llm.py`, retries, token budgets and routing.
- **Part D – Policy RAG assistant and refund agent:** TF-IDF retrieval over five policy documents, a ReAct-style refund agent with five tools, stop-safely guards and crash-and-resume.

The analysis lives in four Jupyter notebooks, one per part, which are executed in order. All model calls go through the supplied offline `mock_llm.py` (no API key, account or network). `generate_data.py` and `mock_llm.py` are unmodified. Analysis libraries: standard library, pandas, numpy, scikit-learn, joblib. Jupyter (`nbconvert`, `ipykernel`) is used only to run the notebooks. Random seed 42 wherever randomness appears.

## Reproduce

Run from the repository root (Python 3.11 or newer). The notebooks must be run in order, because each part reads the outputs of the previous one. `nbconvert` runs each notebook with `src/` as its working directory, which is what the notebooks' relative paths (`../data`, `../outputs`) expect.

1. `python -m venv .venv`
2. Activate it: `source .venv/bin/activate` (macOS/Linux) or `.venv\Scripts\activate` (Windows)
3. `pip install -r requirements.txt`
4. `python generate_data.py`
5. `jupyter nbconvert --to notebook --execute --inplace src/part_a.ipynb`
6. `jupyter nbconvert --to notebook --execute --inplace src/part_b.ipynb`
7. `jupyter nbconvert --to notebook --execute --inplace src/part_c.ipynb`
8. `jupyter nbconvert --to notebook --execute --inplace src/part_d.ipynb`

Each notebook prints its checkpoint values; they should match the tables below. Scikit-learn values (K-Means, PCA, forests) may differ slightly across versions. Alternatively, open each notebook in VS Code or Jupyter and choose Run All, in the same order.

### Lapse prediction

Cutoff 2025-09-01. Cohort: customers with at least one completed order before the cutoff. Target `lapsed = 1` if there is no completed order between 1 and 30 September 2025. Features use only orders before the cutoff: recency, frequency, monetary, average discount, cancellation rate, average delivery minutes, favourite category, city, age, gender and tenure in days. Segment ID, name and Premium flag are not features.

| Cohort check | Value |
|---|---:|
| Eligible customers | 1,156 |
| Lapsed | 443 |
| Lapse rate | 38.32% |
| Train / test (stratified 80/20, seed 42) | 924 / 232 |

Preprocessing: `StandardScaler` on numeric columns and `OneHotEncoder(drop="first")` on city, gender and favourite category. Both are fitted on the training split only, inside a scikit-learn `Pipeline`.

**Baseline** (always predict "not lapsed"): accuracy 0.6164, lapsed precision, recall and F1 all 0. Accuracy alone is misleading for this problem.

**Tuning** (5-fold CV, F1 scoring):

| Model | Grid | Best parameters | CV F1 |
|---|---|---|---:|
| Logistic Regression (`max_iter=1000`) | C ∈ {0.01, 0.1, 1, 10, 100} | C = 100 | 0.6506 |
| Random Forest (`n_estimators=100`, `random_state=42`) | max_depth ∈ {3, 5, 8}, min_samples_leaf ∈ {5, 10, 20} | max_depth = 8, min_samples_leaf = 10 | 0.6811 |

**Test-set results:**

| Metric | Logistic Regression | Random Forest |
|---|---:|---:|
| Precision | 0.6444 | 0.6591 |
| Recall | 0.6517 | 0.6517 |
| F1 | 0.6480 | 0.6554 |
| TP / TN / FP / FN | 58 / 111 / 32 / 31 | 58 / 113 / 30 / 31 |

**Selected model: Random Forest.** It has the higher CV F1 (0.6811 vs 0.6506) and the higher test F1 and precision at equal recall. False negatives are lapsing customers who get no retention offer; false positives are offers spent on customers who would have stayed.

### Class-balance experiment

Lapsed rows in the training split were duplicated with replacement until the classes matched (570 vs 570). Logistic Regression was refit on this data and scored on the untouched test split.

| Logistic Regression | Precision | Recall | F1 |
|---|---:|---:|---:|
| Original | 0.644 | 0.652 | 0.648 |
| Oversampled training data | 0.589 | 0.854 | 0.697 |

Oversampling raised recall (0.652 → 0.854) at the cost of precision (0.644 → 0.589), a net gain in F1. It is useful when missing a lapse costs more than a wasted offer.

## Part D

**Notebook:** `src/part_d.ipynb`.
**Outputs:** `outputs/agent_runs.jsonl`, `outputs/refund_ledger.jsonl`, `state/`.

### Policy retrieval (RAG)

Five policy files (`delivery`, `escalation`, `payment`, `privacy`, `refund`) were split into word chunks (40 words, 10-word overlap), giving **15 chunks** (delivery 3, escalation 3, payment 3, privacy 2, refund 4). TF-IDF gives a 15 × 200 matrix; cosine similarity returns the top 3 chunks, and the answer is the best sentence from the top chunk. If no chunk is relevant, the assistant answers "I could not find that information in the policies."

| Evaluation (14 questions: 12 answerable, 2 unanswerable) | Overlap 10 | Overlap 0 |
|---|---:|---:|
| Expected document in top 3 | 12/12 | 12/12 |
| Expected fact in answer | 12/12 | 10/12 |
| Correct fallback on unanswerable questions | 0/2 | 0/2 |

Overlap protects facts that straddle a chunk boundary: removing it loses two facts.

### Agent design

The agent has five tools: `get_order`, `search_policy`, `calculate_refund`, `issue_refund`, `escalate_to_human`. It loops through model calls and tool executions, with limits of 6 model calls, 6,000 tokens and 10 seconds. Refund rules: only completed orders qualify; delivery over 45 minutes gives a full refund; refunds up to ₹1,000 are issued automatically; above ₹1,000 they go to a human lead.

### Crash and resume

S1 was run with a simulated crash after the second tool observation. The checkpoint in `state/S1_CRASH_RESUME_DEMO.json` recorded `get_order` and `search_policy` as complete and left one pending call. Resuming the run from the checkpoint finished the workflow.

Tools executed across both runs, in order:

1. `get_order`
2. `search_policy`
3. `calculate_refund`
4. `issue_refund`

Final status: REFUND, final refund ₹128.25 (5 model calls, 1,597 tokens, matching the uninterrupted S1 run). Each tool executed once, with none repeated after the resume.

### ReAct vs Plan-and-Execute

ReAct alternates model calls with tool executions. In this workflow S1 needed 5 model calls, S5 3 and S6 2, and each call carries the growing history, so token use rises. Plan-and-execute asks the model for the full step list in one call, runs it in Python, and replans only on error. That would use fewer calls for plain refunds.

Refunds depend on conditions only known after tool calls: cancelled orders, missing orders, delivery time and the ₹1,000 threshold. If `get_order` returns `NOT_FOUND`, a ReAct agent stops straight away, whereas a pre-built plan must notice the surprise and replan safely. For financial actions I would choose **ReAct**, because every decision is based on a verified observation, and accept the extra model calls.

## Limitations and Next Steps

- **Leakage in the retention list.** The Premium flag comes from RFM segmentation up to 2025-10-01, which includes September, the month used to define the lapse label. The retention list is illustrative, not a leakage-free evaluation of targeting. A production version should compute Premium status from data before the prediction date.
- **Modest model quality.** Test F1 is about 0.65 and the test set is small (232 customers; 40 Premium). Results should be validated on a later time period.
- **Imputation and outliers.** Ages are imputed and 897 high-value orders were kept as genuine, which affects spend and RFM statistics.
- **Mock LLM.** Ticket classification and agent behaviour use an offline mock, so accuracy (85.7% zero-shot, 100% few-shot) will not carry over to a real model. Real models also bring latency, cost and non-determinism.
- **Retrieval.** TF-IDF matches words, not meaning, and the fixed-size chunks can split a policy sentence. The assistant did not correctly refuse the two unanswerable questions in the evaluation.
- **Refund ledger.** Every run appends to the ledger, so re-running `part_d.ipynb` adds new rows (the crash demo re-issues the S1 refund for ORD-100048). A production system should make refunds idempotent per order.
- **Next steps:** time-based validation; tune the classification threshold against campaign cost; try gradient boosting; use embedding-based retrieval; add idempotency keys and human approval tracking for refunds; monitor drift and rebuild segments periodically.
